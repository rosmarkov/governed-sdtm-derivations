# Governed SDTM derivations

What AI-generated SDTM derivation code needs in order to be both correct and usable in a production framework, and where prompting stops working.

This repository is the durable home for the poster **"Which SDTM Specification Artifacts Matter Most for AI-Assisted Code Generation?"** (2026 CDISC US Interchange, Denver) and for the talks and paper behind it.

Author: Rostislav Markov, Amazon Web Services.

## The question

AI can draft an SDTM derivation function in seconds. A regulated workflow still needs that function to be correct and to fit the project framework. Which engineering artifacts improve both, and where does prompting stop working?

## Headline results

Eight production-derived SDTM functions were regenerated by one model (Claude Sonnet 4.6 via Amazon Bedrock) under three levels of engineering context. The model and the target functions were fixed; only the context supplied to the model varied.

| Context level | What the model received | Functional correctness | Integration quality |
|---|---|---|---|
| A1 Function description | Brief prose only | 20% | 0% |
| A2 Behavioral specification | Gherkin scenarios with concrete input rows, expected values, edge cases, exact error messages | 84% | 0% |
| A3 Governed specification | A2 plus project conventions, tests, types, helper interfaces | 90% | 70%, rising to 82% after three rounds of convention refinement |

Behavior examples fixed semantics. Project conventions fixed integration. Better context moved the failure mode from semantic errors (wrong algorithm) to mechanical errors (wrong import path). Details in [docs/experiment.md](docs/experiment.md).

## Failure modes

Every observed failure pointed to a missing artifact rather than to a "hallucination":

| Observed failure | Missing artifact |
|---|---|
| Wrong logic | Behavior examples |
| Inconsistent style | Project conventions |
| Wrong imports | Dependency context |
| Wrong input structure | Metadata and schemas |
| Does not fit the system | Architecture context |
| Reinvented utilities | Capability registry |

Worked examples, the integration failure list and the scoring rubrics are in [docs/failure-modes.md](docs/failure-modes.md).

## The plateau, and why it exists

Refining conventions across three runs raised integration quality from 70% to 81% to 82%, while the number of addressable deviations fell from 19 to 7 to 6 and then stalled. The survivors sat where the model has a strong pretrained default. A follow-up study on constraint compliance under strong pretraining priors is in progress; see [docs/plateau.md](docs/plateau.md) and [follow-up/](follow-up/).

The direction of travel is not longer prompts. It is durable, reviewable, reusable specifications: from prompt engineering to specification engineering, with a control boundary where AI may author but only approved artifacts execute.
